# Refreshing SharePoint-derived sales data + the "Top" charts

When the user updates the SharePoint/OneDrive master Excel ("Dummy Master Data Cuci Xpress Sales.xlsx") — e.g. a plate that was previously blank becomes extractable — the way to get it into the DB and into the admin charts:

1. Run `scripts/sharepoint_import_history.ts` (idempotent; skips rows already imported by `legacy_source_row_number`, so previously-skipped rows like a blank-plate row get picked up once the plate is filled). It upserts `cars` by normalized plate, inserts `orders` with `legacy_source='sharepoint'`, then refreshes `cars.total_visits` / `total_spent_cents`.
2. Then run `scripts/recompute_vip_tiers.ts` (cheap, <1s) to re-rank VIP tiers.

**Why both:** The admin Top Brands / Top Models / Top Customers charts are computed **live** from `cars`+`orders` (no materialized views, no cache), so the import alone updates brand/model/spend instantly. BUT `cars.vip_tier` / `vip_rank` (the Gold/Silver/Bronze segments the Top Customers view uses) are stored columns refreshed only by the recompute script — without it, tier labels go stale.

**How to run a long import in this sandbox:** the full scan is ~130k rows and takes ~25-30 min (Graph API rate-limits with 503/504 + backoff). Do NOT use `nohup`/`setsid &` — the sandbox kills detached processes (0-byte log). Foreground bash caps at 120s. Create a temporary console workflow (`configureWorkflow({name, command, outputType:'console'})`, tee to a log), poll the log, then `removeWorkflow`.

**WARNING — the workflow supervisor RESTARTS the script if it's killed mid-run.** A ~30min one-shot got SIGKILLed near the end (~113k/135k) and the supervisor relaunched it from row 1 → infinite re-scan loop burning Graph quota. Mitigation: (a) the importer is idempotent (skips `legacy_source_row_number` already in `orders`) so re-runs resume and fill holes; (b) watch the log and `removeWorkflow` the moment it either finishes OR you see it restart from the top; (c) for the real 7pm run, expect to re-run until it exits 0. The importer now FAILS LOUDLY (exit 1, cars-aggregate refresh SKIPPED) if any Graph chunk exhausts retries or any row INSERT errors — so a partial run can never masquerade as complete. Re-run until `failedChunks: 0` and exit 0.

**Full legacy reconciliation rules (owner-approved, to match the Power BI Excel master net total).** When importing ALL remaining legacy rows (not just new-plate rows), the importer applies: (1) **no-plate rows import too** — `vehicle_id NULL`, `plate=''` (orders.plate NOT NULL), NOT car-linked; (2) **Pandan = a real CLOSED branch** — ensure-branch INSERT with `is_active=false,status='closed'`, import its sales under it, and `/api/queue/snapshot` filters `COALESCE(is_active,true)=true` to hide it from the public live queue while reports still count its history; (3) **plain store name "Cuci Xpress" = the ORIGINAL Tungku name** → alias-mapped to Tungku's branch id; (4) **refunds import** as `status='refunded'` with a POSITIVE `total_cents` (Math.abs — CHECKs forbid negatives) + `refunded_at` + `refunded_by_staff_id`=owner (satisfies `orders_refund_fields_consistent`); the report nets them out. **App-mirrored rows must be skipped:** the outbox writes every app order back into the same sheet with `Source.Name` (col A) = `cucixpress_pos` (starts ~rownum 132824); importing them would double-count, so the loop skips them. Refunds & no-plate rows are never car-linked (`linkCar = hasPlate && !isRefund`) so cars visit/spend aggregates stay honest.

**Data-quality gotcha:** brand/model casing in the source is inconsistent (e.g. `BMW`/`X3` vs `bmw`/`x3`), so the same model can split into two chart rows. Stored verbatim from the Excel `Extracted_Brand`/`Extracted_Model` columns. Only normalize if the user asks.

**Dedup is by ROW POSITION, not content.** The importer skips rows whose 1-based `legacy_source_row_number` (position in the table body, header excluded) is already in `orders`. This is ONLY safe when new data is **appended at the bottom** in the existing order. If the user re-sorts the sheet or inserts rows mid-table, positions shift and a re-import will both duplicate and mis-map. **Before any incremental re-import: peek the boundary** — confirm the last-imported row number still holds the same date/plate it did at import time, and that newer rows sit strictly after it. Use `--start-row=<n>` to begin the Graph scan at the first new row so you don't re-fetch ~130k already-imported rows just to skip them (turns a ~15min job into one chunk).

**Deleting webapp orders (e.g. clearing test/seed data, `legacy_source IS NULL`):** orders has a two-way loyalty link — `loyalty_redemptions.voucher_order_id -> orders.id` AND `orders.loyalty_consumed_in -> loyalty_redemptions.id`. A plain delete hits `orders_loyalty_consumed_in_fkey`. Order: NULL `orders.loyalty_consumed_in` first, then delete `sharepoint_outbox`, `loyalty_redemptions`, `membership_redemptions` children, then orders, all in one txn; finish by recomputing `cars.total_visits`/`total_spent_cents` then `recompute_vip_tiers.ts`. Imported rows are `status='done'` so they never re-enqueue to the outbox.
